# The X16 lane: bit-exact CPU experts (`x16_layers`)

`x16_layers=N` (both backends, mode `nvme`, off by default) puts the CPU lane of the first `N` MoE layers on the X16
path: the experts the CPU computes there come out bit-identical to what exllamav3's GPU kernel computes, so those
layers equal exact decode (`nvme-exact`) while the CPU still takes part of their work.

```python
AutoBox("glm-5.3-flash", x16_layers=21)          # Python
```
```
bigmoe start glm-5.3-flash -o x16_layers=21      # CLI (also bigmoe bench / verify -o x16_layers=21)
```

Every start self-tests each X16 layer (a token with half of its picks on the CPU, against the GPU kernel on all of them)
and leaves the lane off, with a log line, unless every layer is bit-identical. Layers whose MoE the lane cannot
reproduce (expert biases, gateless experts, other activations, latent or tensor-parallel MoE) end the X16 range.

## Results (RTX 3090, Ryzen 5 7600X, 2026-11-05)

Agreement: forced decode of the same tokens as the exact reference, top-1 agreement and mean KL(exact || this).

| model | configuration | top-1 | mean KL | decode 1k / 8k prompt |
|---|---|---|---|---|
| GLM-5.3-Flash | `nvme` (default) | 97.2 % | 0.012 | 11.21 / 11.31 tok/s |
| GLM-5.3-Flash | `nvme`, `x16_layers=21` | 99.33 % | 0.0012 | 9.94 / 10.25 tok/s |
| GLM-5.3-Flash | `nvme-exact` | 100 % | 0 | 7.74 / 7.84 tok/s |
| DeepSeek-V4.1-Flash | `nvme`, DSpark (default) | 99.6 % | 0.0008 | 16.43 / 19.81 tok/s |
| DeepSeek-V4.1-Flash | `nvme`, no speculation | 99.3 % | 0.0013 | 14.15 / 16.70 tok/s |
| DeepSeek-V4.1-Flash | `nvme`, no speculation, `x16_layers=40` (all) | 100 % | 0 | 11.32 / 12.83 tok/s |

GLM speeds: `bigmoe verify` (also 32k: 11.43 -> 9.74, 120k: 11.45 -> 10.11 tok/s); DeepSeek: `bigmoe bench`; the

X16 only serves single-token forwards: with DSpark on, the verify forwards of X16 layers run their experts on the GPU.

For GLM, 21 layers is where the gain is (below). For DeepSeek the ordinary lane is already at 99.3 %; X16 on every layer
makes decode exact, at about the speed of `nvme-exact` with DSpark (README: 11.0 / 12.6 tok/s).

## Why the ordinary CPU lane diverges from the GPU

Both sides start from the same bytes: EXL3 trellis-coded weights (a 16-bit window of the bitstream per weight, hashed
into a codebook value) and the same fp16 activations. They then compute the same dot products with different rounding.

**What the GPU computes** (exllamav3's fused decode MoE kernel, `exl3_moe_coop_kernel.cuh`, on Ampere):

- Each weight is decoded to an **fp16** value (`hfma(half(1024 + s), K, B)`, rounded once to fp16).
- The activation is rotated (`x * suh`, 128-point Hadamard) and stored as **fp16**.
- Products are summed on the tensor cores with `mma.sync.m16n8k16 ... f16.f16.f16.f16`: the accumulator is
  **fp16**. Measured semantics (a probe kernel against models of the arithmetic, 100 % of 2.5M outputs over six input
  distributions): every 8 products, the accumulator `c` becomes
  `RN16( sum of trunc0(t, 2^(emax - 24)) )` over `t = {c, x_k * w_k}`, where `emax` is the largest *alignment*
  exponent (`e(x) + e(w)` from the inputs' exponent fields, fp16 subnormals counting as -14) and `trunc0` truncates
  toward zero. Every term is cut 24 bits below the largest one, the cut terms are added exactly, and the sum is
  rounded to fp16 once. (Plain "exact sum, then round" matches 99.988 % of outputs, truncation relative to the
  products' own exponents 99.9986 %; only alignment-exponent truncation matches all.)
- Every 64 rows the fp16 accumulator is added to an **fp32** sum; four warps split the rows into equal ranges and sum
  their folds in order, then the four warp sums are added in order.
- Gate / up results are stored as **fp16**; the epilogue (Hadamard, scales, SiLU with `__expf` / `__fdividef`) runs in
  fp32 with fast-math hardware approximations and stores the down input as **fp16**; the down projection is summed the
  same way and kept in fp32; the token's experts and the shared expert are added in a fixed order.

**What the ordinary CPU lane computes** (`nv2/ft_n135.h`): activations quantized to int16 per 128-element block,
integer dot products (AVX-512 VNNI / AVX2) accumulated in int32, weights taken from the codebook's affine form
without the fp16 rounding, partial sums in fp32 in its own order.

Both are accurate approximations of the same mathematical result, but they are different approximations:

| per-expert output vs the GPU's (relative error) | |
|---|---|
| GPU kernel vs fp64 of the same weights | ~8e-4 |
| CPU lane (int16 activations, int32 sums) | ~9.4e-4 |
| CPU with fp32 activations and fp32 sums ("EXACT" mode) | ~8.6e-4 |
| CPU with fp16 weights and an approximate fp16-accumulator emulation | ~2.5e-4 |
| X16 | 0 |

Making the CPU *more precise* does not bring it closer to the GPU: the GPU's own result is ~8e-4 away from the exact
one, and the CPU lands somewhere else in that neighbourhood.

## Why tiny differences matter for GLM

For DeepSeek, the ordinary lane's ~1e-3 per-expert differences cost little (99.3 % top-1). For GLM-5.3-Flash they cost
3 points, and the experiments say it is not a matter of size:

- Reducing the lane's error 4x (2.5e-4) did not help (97.7 %); adding 3 % noise to it did not hurt (97.9 %).
- Keeping layers 0-20 exact on the GPU and adding relative Gaussian noise of 1e-4, 1e-5 or 1e-6 to their MoE outputs:
  97.7 %, 96.7 %, 96.9 %, as bad as the ordinary lane. Any change at all saturates.
- The CPU lane in layers 21-41 only: 99.2-99.3 %, KL 0.0011 (DeepSeek level). In layers 0-20 only: 97.7 %,
  KL 0.0099. In layer 20 alone: 99.0 %, KL 0.0018.
- The KL is heavy-tailed (the worst 1 % of positions carry ~45 % of it).

So GLM's early MoE layers amplify any perturbation of their output into a different downstream distribution; the only
way to keep DeepSeek-level agreement there is bit-identical results: the GPU computing those experts itself (CPU lane
off there: same agreement, but those layers become PCIe-bound, decode -16 % on short prompts), or X16.

## How X16 gets the GPU's bits

1. **CPU, gate and up** (`nv2/ft_x16.h`, `rect_x16`): weights decoded as the GPU does and rounded to fp16; products
   exact in fp32 (11 x 11-bit mantissas); each term scaled by `2^(24 - emax)` and truncated to int32
   (`vscalefps` + `vcvttps2dq`, exact); the int32 terms summed exactly; the sum rounded to fp16 once (round-to-odd to
   fp32, then nearest-even to fp16, which is exact because fp32 keeps more than 11 + 2 bits); folds and warp sums in
   the kernel's order. The input rotation (`prep_block_v`) already matched the GPU's bit for bit.
2. **GPU, activation** (`x16_epa`): the CPU cannot reproduce `__expf` / `__fdividef` (hardware approximations), so the
   GPU runs exllamav3's epilogue code (copied verbatim, built with exllamav3's flags) on the CPU's fp16 rows.
3. **CPU, down**: the same kernel on the GPU's fp16 activations, kept in fp32 as the GPU does.
4. **GPU, reduction** (`x16_red`): exllamav3's per-token sum over every picked expert in slot order (the GPU's own down
   outputs and the CPU's) plus the shared expert, so the layer output is exactly the full kernel's.

Scheduling details that mattered: the CPU and GPU hand off through host-mapped flags; the epilogue is one block on a
high-priority, non-blocking side stream (torch's compute stream is the legacy default stream, which serializes with
ordinary streams); a tiny main-stream kernel holds the layer's MoE kernels until that block is resident (otherwise it
waited ~1 ms for SMs); and the block is never resident outside its layer call, because exllamav3's prefill GEMMs are
cooperative launches that deadlock if any SM is occupied. The planner only gives X16 layers RAM-resident picks of
single-token forwards, costed at 5.5x an ordinary CPU expert.

**Cost.** The X16 kernel takes 2.4 ms per 4096 x 2048 matrix on one core, 5.5x the ordinary kernel (0.43 ms); in the
engine an X16 expert costs ~1.6 ms of CPU time against 0.41 ms for an ordinary one and 0.44 ms to stream the expert to
the GPU over PCIe. The CPU can therefore take over only about one expert per layer in GLM's early layers: on short
prompts X16 in layers 0-20 cost 14 % of decode speed, turning the lane off there 16 %. Micro-optimizations (integer exponents, integer
rounding, `vrangeps`), SMT threads and an "estimate in fp32, fall back when near a rounding boundary" fast path each
gained less than 6 % or lost.

## Would INT32 accumulation fix it?

Not on its own. The ordinary lane already accumulates in int32; the problem is not that the CPU loses precision but that
its result is not the GPU's result. A CPU with exact int32 (or fp64) sums gets closer to the mathematically exact dot
product, which is ~8e-4 away from what the GPU computes; the measured "more precise" CPU variants above confirm this.
Agreement is measured against the GPU kernel, so the CPU has to reproduce the GPU's rounding, not avoid it.

X16 does use exact int32 accumulation, but of terms that have first been truncated onto the GPU's grid, with the fp16
rounding applied where the GPU applies it (every 8 products, at the fp16 stores) and the fp32 additions in the GPU's
order. Int32 is the tool that makes the emulation exact, and the emulation is what makes it cost 5.5x.

The other direction would be to change what "exact" means: a GPU kernel whose arithmetic is cheap to reproduce exactly
on the CPU (integer products with exact accumulation and a single rounding at the end, a deterministic activation
function). That has not been tried, and it is a redesign rather than a fix: it replaces exllamav3's kernels and its
reference results (today's `nvme-exact` outputs would change); exllamav3's weights are fp16 codebook values with 11-bit
mantissas, so exact products need ~22 bits and exact sums ~30 or more, while Ampere's integer tensor cores multiply
int8 / int4 into int32 (int16 weights would mean several int8 MMAs per product); and the epilogue would need an
activation the CPU can compute bit-identically.

## Limits

- The MMA semantics were measured on an RTX 3090 (Ampere, sm_86) and are exllamav3's decode kernel on that path
  (identical in exllamav3 1.5.1 and 1.6.6 for Ampere). Other GPUs may round differently; the start-up self-test
  checks each layer and keeps the lane off if it is not bit-identical.
- Needs AVX-512 VBMI (Zen 4, Ice Lake or later) and EXL3 experts with the mul1 codebook at K 2, 2.5 or 3.
- Single-token forwards only; experts arriving from NVMe stay on the GPU in X16 layers.
